# OJ-Ssystem 技术亮点、难点与架构展望

> 面向评审/汇报：提炼 **3 个技术亮点**、**4 个技术难点**、**3 个未来架构改进方向**。  
> 依据当前仓库实现（Spring Boot 3、Spring Cloud Alibaba、Gateway、Nacos、MySQL、Redis、RabbitMQ、Elasticsearch、Docker 判题等）。

---

## 一、三个技术亮点

### 1. 容器化判题与链路的异步解耦（RabbitMQ）

- **现象**：`oj-friend` 接收提交后在表 `tb_friend_code_submit`中预创建记录并写入，将 **判题消息** 发往 RabbitMQ；`oj-judge` 侧 `@RabbitListener` 消费并通过容器池创建容器，后调用 `JudgeRunService` 在容器中完成编译、运行、比对。
- **价值**：一方面隔离机制隔离恶意代码，保证jvm运行的安全性；同时提交接口快速返回，判题耗时与吞吐由 **判题服务 + 队列** 承担，避免同步 HTTP 压垮 friend 或长连接超时。

### 2. 阿里云OSS存储逻辑的优化

- **现象**：数据库存储图片的全量路径，如果前端被劫持，可能会出现存储有害路径的情况，损害用户的隐私权
- **优化1**：将路径前缀通过配置的形式写死，数据库只存储 **object key** （路径后缀），通过如果需要查询图片路径，通过拼接的方式得到完整的路径
- **价值1**：优化1可以解决如果前端被劫持，也只能在指定前缀的目录中作乱，无法跳转到更危险的链接
- **优化2**：禁止使用主用户的权限，通过创建RAM用户并严格控制权限，比如限制到目标 bucket 的指定前缀（如 oj/avatar/*）
- **价值2**：优化2可以解决前端权限过大导致如果被劫持，损害OSS中存储的各种信息

### 3. AOP实现 Prometheus + Grafana 链路实时监控（Actuator + Micrometer + Prometheus + Grafana）

- **现象**：各微服务引入 **Spring Boot Actuator** 与 **Micrometer Prometheus Registry**，暴露 **`/actuator/prometheus`**；**Prometheus** 按配置 **周期性拉取（pull）** 各实例指标并落库；**Grafana** 对接 Prometheus 做大盘与 Explore 查询。业务侧通过 **`oj-common-AOP`** 对登录/注册、判题 compile·run、XXL-JOB 等做 **Counter/Timer 埋点**，统一注册到 **MeterRegistry**，与 JVM/HTTP 等默认指标一并被采集。
- **价值**：**监控链闭环**：应用进程内埋点 → 文本指标端点 → Prometheus 存储 → Grafana 可视化；便于观察 **QPS、耗时、业务次数** 与 **Targets 健康**，为容量与排障提供数据基础（详见《Prometheus与Grafana监控指南.md》及仓库目录 `oj-prometheus`）。

## 二、四个技术难点

### 1. 不可信代码的执行安全与资源边界

- **难点**：用户代码可能死循环、爆内存、读写敏感路径或滥用进程；需在 **CPU/内存/时间/文件系统/网络** 等维度限界。
- **现状依赖**：Docker 隔离、`tmp-judge` 独立工作目录、题目侧 `timeLimit`/`spaceLimit` 等参与判题参数传递；更细粒度还需结合镜像、seccomp、cgroup 等与运维策略（参见《OJ判题系统安全技术文档》）。

### 2. ES 与 MySQL 的语义一致与延迟

- **难点**：ES 非强一致存储；当前以 **回源 + 回填** 为主，管理端若改题未同步 ES，可能出现 **短暂旧数据或检索空窗**。
- **影响面**：检索结果、判题读题路径均可能读到滞后副本；需从产品设计或同步链路上接受 **最终一致** 或补齐 **写路径双写**。

### 3. 异步判题下的状态与用户体验

- **难点**：提交后立即返回 `PENDING`，用户依赖 **轮询/查询结果接口**（如按 `submitId` 拉状态）；需处理 MQ 堆积、判题失败、 poison message（项目中有 DLX 相关常量，需与运维策略结合）。
- **关联**：判题服务扩缩容、队列监控、失败重试与 **死信** 处理若不完善，易出现长时间 `PENDING` 或结果不一致感知。

### 4. 监控自动装配类与 MeterRegistry 的加载顺序（`OjMetricsAutoConfiguration`「看似失效」）

- **背景**：业务埋点集中在公共模块 **`oj-common-AOP`** 中，通过 **`OjMetricsAutoConfiguration`**（Spring Boot **`@AutoConfiguration`**）统一注册 **`@Aspect` 切面 Bean**；切面在 **`@Around`** 里使用 **`MeterRegistry`** 创建 **Counter / Timer**，与 **Micrometer** 对接，最终由 **Actuator** 的 **`/actuator/prometheus`** 对外暴露，供 **Prometheus** 抓取。

- **现象（表面上的「失效」）**：服务启动无报错，但访问 **`/actuator/prometheus`** 时，**看不到** 预期的业务指标（如 `user_actions_total`、`judge_operation_seconds_*`、`xxl_job_executions_total`），容易误判为 **「AOP 没有织入」** 或 **「Prometheus 配错了」**。

- **根因（自动配置顺序问题）**：  
  Spring Boot 在启动时会按一定顺序处理大量 **自动配置类**。**`MeterRegistry` Bean** 由 Actuator 侧的 **`MetricsAutoConfiguration`**（及后续 Prometheus 导出相关配置）创建；若自定义的 **`OjMetricsAutoConfiguration` 执行得过早**，在处理该配置类的 **`@Bean` 方法**时，若使用了 **`@ConditionalOnBean(MeterRegistry.class)`**，此时 **容器中可能尚未注册 `MeterRegistry`**，条件判定为 **不满足**，则 **对应的切面 Bean 整组不会被注册**。  
  其结果是：**切面类从未作为 Bean 存在**，Spring AOP **不会** 为它们生成代理，业务代码路径上 **根本不会执行** 埋点逻辑——这不是编译期 AspectJ 织入失败，而是 **运行时 Bean 未创建**。
  **究其根本，就是OjMetricsAutoConfiguration类加载过早，导致没有MeterRegistry能为其服务，导致OjMetricsAutoConfiguration类被跳过。通过增加注解@AutoConfigureAfter的方式强制指定加载顺序，保证OjMetricsAutoConfiguration类能在MetricsAutoConfiguration类后加载**

- **为何容易误判**：  
  从现象上看「没有业务指标」，开发者往往会先查 **切点表达式、Prometheus `targets`、防火墙**，而忽略 **自动配置与条件注解的先后关系**；实际上 **`@ConditionalOnBean` 的评估时机**与 **`MeterRegistry` 的创建时机** 一旦错位，就会出现 **静默失败**（无异常栈，仅缺指标）。

- **处理思路（本项目采用）**：  
  1. 在 **`OjMetricsAutoConfiguration`** 上增加 **`@AutoConfigureAfter(MetricsAutoConfiguration.class)`**，**显式保证** 在 **`MetricsAutoConfiguration` 完成之后再处理** 本配置类，使 **`MeterRegistry` 已可用**。  
  2. **去掉** 各切面 **`@Bean` 上的 `@ConditionalOnBean(MeterRegistry.class)`**（避免与顺序判断重复踩坑），改为在 **`@Bean` 方法参数中直接注入 `MeterRegistry`**——由 Spring 在创建该 Bean 时解析依赖，此时 **`MeterRegistry` 已存在** 即可。  
  3. **`oj-common-AOP`** 的 Maven 中 **`spring-boot-actuator-autoconfigure`** 使用 **`provided` 作用域**，仅用于 **编译期引用 `MetricsAutoConfiguration` 类名**，运行时仍由业务服务自带的 Actuator 提供实现。

- **小结**：该问题本质是 **Spring Boot 自动配置顺序与条件装配** 与 **可观测性基础设施 Bean（`MeterRegistry`）** 的 **依赖先后** 问题；修复后，业务指标才会稳定出现在 Prometheus 抓取路径中。更细的组件关系见《Prometheus与Grafana监控指南.md》**§3.2、§3.6、§5.6**。

## 三、三个未来架构改进点

### 1. 服务扩展

- **方向**：多实例 `oj-judge` 并发消费；数据库的分库分表；分布式事务一致性的方案等
- **收益**：高峰时稳定 RT；避免单点故障成为系统瓶颈。

### 2. 数据同步与搜索/读题一致性策略产品化

- **方向**：管理端题目/竞赛变更时 **同步写 ES**、或 **Canal/Debezium** 订阅 binlog、或 **定时校验对账**；对强一致场景提供 **版本号** 或 **读主库回退** 策略。
- **收益**：减少「搜不到题」「判题读到旧题面」的边界客诉。

### 3. 可观测性与运维闭环

- **方向**：网关—friend—MQ—judge 全链路 **TraceId**；判题耗时、队列积压、DLQ 率、沙箱失败原因 **指标与告警**；关键表状态机可视化。
- **收益**：快速定位「卡在 PENDING」「某类 CE 暴增」等问题，缩短 MTTR。
